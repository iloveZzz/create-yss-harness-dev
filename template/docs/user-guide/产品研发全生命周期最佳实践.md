# Harness Agent 研发落地最佳实践

本分支已采用新的 `harness-agent` 体系；本文保留文件名以兼容文档链接，内容以当前五阶段流程为准，不再描述旧的产品、商务、需求、项目管理多角色体系。

## 目标

面向架构、前端、后端和测试四类研发角色，从已批准的上游 Spec / 战略设计出发，在 DDD 战术设计层完成可审查、可实现、可验证的产品研发落地。

## 推荐流程

1. `harness-entry`：读取 `yss-project.yaml`、`CONTEXT.md` 和上游批准资产，判定影响面并登记实现仓库、写路径、命令和回滚点。
2. `tactical-design`：架构 Agent 形成 DDD Tactical Design Contract；测试 Agent 建立早期验证 seam。
3. `slice-contract`：Harness Orchestrator 汇合 `architecture`、`frontend`、`backend`、`testing` 四个分区，编译并批准统一 Slice Implementation Contract。
4. `slice-implementation`：前端和后端按合同并行实现，测试 Agent 持续维护 seam；任何合同漂移都暂停并重路由。
5. `verification`：测试 Agent 独立执行 Fresh Verification，形成可追溯证据并决定是否进入合并会签。

## 关键实践

- 先设计行为，再落代码：聚合、不变量、状态机、一致性和 Gateway 先进入 Tactical Design Contract。
- 一个切片一份合同：四个 Agent 必须引用相同 `contract_id` / `contract_version`，不得按技术层拆成互相失联的任务。
- 测试先于实现：先定义公开 seam、fixture、验收和验证命令，再进入前后端实现。
- 工具命令固定：前端优先 `pnpm`，后端优先项目根 `./mvnw`；受控例外必须记录。
- 证据必须新鲜：实际命令、退出码、耗时、时间戳和证据引用缺一不可。
- 权限和安全只按实际行为影响进入普通契约与验收，不凭空创建额外流程。
- Harness 仓库不默认承载业务代码；独立实现仓库、`harness-apps` 和 `git-submodule-harness-apps` 必须按登记字段区分。

## 角色边界

`role.architecture-agent` 负责 Tactical Design 和架构边界；`role.frontend-agent` 负责前端垂直切片；`role.backend-agent` 负责 DDD 后端垂直切片；`role.test-agent` 负责独立测试和验证。`role.harness-orchestrator` 是编排组件，不计入四类角色，也不写业务实现。

## 完成门槛

只有当上游输入、战术设计 / `not-applicable`、API / 数据 / UI 影响、实现仓库、写路径、测试 seam、验证命令和合同版本全部当前有效，且没有 `blocked`、`stale`、`drift`、`violation`、`new_impacts` 时，才可设置 `ready-for-agent`。高风险架构、OpenAPI Freeze 和 `gate.merge-approved` 保留生物人会签。

权威细则见 [`docs/user-guide/产品生命周期工作流.md`](产品生命周期工作流.md)、`AGENTS.md`、`docs/agents/digital-human-roles.yaml`、`docs/process/lifecycle-registry.yaml` 和 `harness-agent-contract-v1`。
