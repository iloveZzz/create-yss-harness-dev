# 通用研发生命周期最佳实践

## 责任先于工具

消费批准 Spec/战略输入，统一组织架构、前后端和测试；不以 Discovery 为默认入口。可继续服务既有通用项目，不要求迁移专职 profile。

整体业务切片可能跨 API、后端、前端和测试；本仓只承担批准合同中实际受影响且属于本 profile 的部分。不得机械要求每个任务修改所有技术层。另一端可只读评审输入，不能在本端派发越界写任务。

## 每次任务的起点

读取本仓身份、根词汇、profile、批准输入、当前合同及依赖。让 Agent 报告目标、允许路径、验证命令和回滚点，缺证据时只诊断；不要用“继续”“全部通过”补齐不存在的批准。

## 协作与验证

1. 一次选择一条可独立验收的用户路径，成功和失败同时设计。
2. 业务语言不一致回交维护方；目标词汇对账后再映射规则和场景。
3. 编译器只起草合同，适用批准与就绪由本仓流程裁决。
4. 实现者与独立 Reviewer 分离；测试记录真实命令、时间和退出码。
5. 前端使用登记工程 pnpm；后端优先根 ./mvnw。覆盖率推荐只有项目明确采纳后才是门禁。
6. 同步、交接或恢复先检查版本漂移，依赖未知时扩大阻断。

## 避免的误用

- 验包成功不等于服务可用、合同获批或业务完成。
- 输入就绪不等于 ready-for-agent。
- 不能用 --force 或删除 metadata 切换家族。
- 专职项目不能用另一端代码实现来补上游缺口。
- 模板维护产物、教学案例不作为真实产品证据。
