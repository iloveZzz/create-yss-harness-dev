# Harness Agent 产品研发工作流

本分支采用 `harness-agent` 体系，目标用户只有架构、前端、后端和测试四类角色。旧的全生命周期入口、产品 / 商务 / 需求 / 项目管理角色不再进入当前分支默认路由。

## 定位

本仓库是研发管理 Harness，不承载默认的业务运行时代码。它保存上下文、战术设计、契约、Ticket、验证证据和回滚点；实际前后端代码按 `docs/process/implementation-repo-integration.md` 登记在独立实现仓库，或按明确授权放入 `apps/backend/<project>/`、`apps/frontend/<project>/`。

权威事实源：

- `CONTEXT.md`：统一语言和稳定协作术语。
- `docs/agents/digital-human-roles.yaml`：四类 Agent、运行时和会签规则。
- `docs/process/lifecycle-registry.yaml`：阶段、门禁、产物、工作单元和证据 ID。
- `.agents/skills/harness-orchestrator/references/orchestration-contract.yaml`：Harness Agent 协作和就绪合同。
- `.agents/skills/yss-router/references/slice-implementation-contract.md`：统一 Slice Implementation Contract 模板。

## 四角色

| 角色 | 责任边界 |
|---|---|
| `role.architecture-agent` | DDD Tactical Design、聚合 / 行为 / 不变量 / 状态 / 一致性、API / 数据边界和 ADR |
| `role.frontend-agent` | 页面、组件、状态、生成客户端消费和前端测试 |
| `role.backend-agent` | Domain、Application、Infrastructure、Web、DTO、数据访问和后端测试 |
| `role.test-agent` | 测试 seam、fixture、契约 / 集成 / E2E、Fresh Verification 和独立审查 |

`role.harness-orchestrator` 是系统编排组件，不计入四类研发角色。它负责入口、影响面、合同版本、任务包、状态转移、证据汇合和重路由，不写业务代码。

## 标准链路

```text
harness-entry
  → tactical-design
  → slice-contract
  → slice-implementation
  → verification
```

执行态统一为 `Explorer / Drafter / Worker / Reviewer / Verifier`。每个功能先建立父 Ticket；每个实现切片消费一个统一的 `slice-implementation-contract-v1`，合同固定包含 `architecture`、`frontend`、`backend`、`testing` 四个分区。

### 1. Harness Entry

读取 `yss-project.yaml`、`CONTEXT.md` 和批准的上游 Spec / 战略设计，登记影响面、实现仓库、验证命令、允许写路径和回滚点。身份缺失、上下文缺失或上游输入过期时直接 `blocked`。

### 2. DDD Tactical Design

有领域行为、聚合、不变量、状态机、一致性、Domain Event、Gateway 或持久化映射影响时，由架构 Agent 使用 `yss-tactical-design` 形成 DDD Tactical Design Contract，并由测试 Agent 评审。没有这类影响时，必须持久化 `not-applicable` 及原因。

### 3. Slice Contract

Router 只编译草案。Harness Orchestrator 汇合架构、前端、后端和测试四个分区，确认 OpenAPI Freeze / 无 API 影响、数据和 UI 输入、实现仓库、写路径、测试 seam、验证命令及合同版本均当前有效后，才可批准合同。

测试 Agent 必须先建立公开测试 seam 和验收矩阵。前端和后端在合同批准后可并行实现，但所有任务包必须引用相同的 `contract_id` / `contract_version`。

### 4. Slice Implementation

前端使用 `pnpm` 完成测试、type-check 和构建；后端在项目根使用 `./mvnw` 完成校验、测试和编译。业务规则、状态机、事务、复杂查询和用户可见交互默认使用 `behavior-tdd`；纯脚手架、冻结客户端和机械配置才可使用受控生成，并必须补生成后行为测试。

未批准合同、路径越界、证据缺失、`drift`、`violation`、`new_impacts` 或验证命令改变时，立即暂停实现并重路由。

### 5. Verification

测试 Agent 独立执行 Fresh Verification，重新记录实际命令、退出码、耗时、时间戳和证据引用。实现者不能担任同一切片的独立验证者。推荐阈值为 Domain / Application `>= 90%`、API `>= 80%`、前端组件 `>= 75%`；关键流程清单中的每条关键流程要求 `100% E2E` 或等价可执行验证。项目实例只有明确采纳后才把阈值作为 CI 门禁。

高风险架构、OpenAPI Freeze 和 `gate.merge-approved` 保留生物人会签。所有运行时外部副作用也由生物人确认。任何“完成 / 可合并”结论都必须基于本轮 Fresh Verification，不接受之前运行过或 Agent 自述。

## 任务包和投影

正式派发必须使用 `docs/process/schemas/digital-human-task-package.schema.json`，从 `docs/agents/digital-human-roles.yaml` 复制技能集合，写明角色、运行时、执行态、合同、输入、允许写路径、验收、验证结果和下游消费者。`.agents/skills` 是 canonical 内容，`.claude/skills`、`.codex/skills`、`.cursor/skills`、`.pi/skills`、`.qoder/skills`、`.trae/skills` 是生成投影，更新后运行 `scripts/sync-skills` 和 `scripts/update-skill-lock`。

详细执行规则见 `AGENTS.md`、`docs/agents/digital-human-roles.md`、`docs/process/subagent-collaboration.md` 和 `docs/process/harness-process-tailoring.md`。模板发布前运行 `scripts/verify-template`。
